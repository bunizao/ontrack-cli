# CLI Normalization Plan — ontrack-cli / moodle-cli / edstem-cli

Status: approved design, not yet implemented.
Scope: three sibling CLIs published by the same author, used by the same humans and the same agents.
Breaking changes are explicitly allowed — none of the three has a stable public contract yet.

This document is the complete specification. An implementer should not need the original audit
conversation. Where a claim comes from measurement, the measurement is stated.

---

## 0. Repositories

| Tool | Path | Binary | Arg parser today |
| --- | --- | --- | --- |
| ontrack-cli | `~/Library/CloudStorage/Dropbox/Dev/ontrack-cli` | `ontrack` | `node:util` `parseArgs` |
| moodle-cli | `~/Library/CloudStorage/Dropbox/Dev/moodle-cli` | `moodle` | `commander` |
| edstem-cli | `~/Library/CloudStorage/Dropbox/Dev/edstem-cli` | `edstem`, `edstem-mcp` | `commander` |

Decisions already made by the owner:

1. Build the shared package `@bunizao/cli-kit`.
2. Migrate ontrack-cli from `parseArgs` to `commander`.
3. Canonical enrolment noun is `units`. `courses` and `projects` are first-class aliases in all
   three tools — every one of the three words works everywhere. Monash calls these units; Moodle
   and Ed call them courses; Doubtfire calls them projects. All three refer to the same object,
   so all three resolve.

## 1. Why

Measured across the three CLIs today:

- **Exit codes collide.** `3` means "usage error" in moodle-cli and "auth expired" in edstem-cli.
  `2` means "auth/config" in moodle-cli and "usage" in ontrack-cli. A wrapper that retries on auth
  failure retries on typos in one tool and never retries real auth failures in another.
- **Three error-code vocabularies** for the same six concepts (`input`/`usage_error`/`usage`, …).
- **Three output-flag systems.** edstem defaults to JSON, the other two to tables. `edstem thread`
  carries `--md`, `--format`, and `--legacy-json` — three overlapping switches on one command.
- **ontrack-cli has no `-h`, no `-V`, no `help <cmd>`.** Verified: `ontrack -h` → `Unknown command: -h`.
- **Singular/plural traps in all three.** `ontrack task` is a command *group*; `ontrack tasks` is a
  *leaf*. One character apart, structurally different.
- **Mutations hidden behind read-shaped names.** `edstem lessons read` issues
  `PUT lessons/slides/<id>/complete` (`src/ed/client.ts:95`). `ontrack chats <p> <t>` marks comments
  read based on positional-argument count (`src/application.ts:143`).
- **edstem hides mutating commands from help** — `lessons answer`, `lessons submit`, and the whole
  `slides` group are suppressed via `hideCommand()` (`src/cli.ts:204-218`).
- **moodle-cli prints every error twice** — commander's plain text plus its own JSON envelope.
  Verified: `moodle courses --bogus` emits both on stderr.
- **moodle-cli has six near-identical top-level commands** (`assign`, `quiz`, `resource`, `link`,
  `page`, `folder`) generated by one factory, `addActivityCommand` (`src/cli.ts:165-170`).

## 2. The contract

Everything in this section is identical across all three tools. Deviation is a bug.

### 2.1 Grammar

```
<tool> <noun> [verb] [scope] [id] [flags]
```

**Nouns are always plural.** No singular/plural pairs may exist.

**Verbs come from this closed set. Nothing else is permitted.**

| Verb | Meaning | Mutating |
| --- | --- | --- |
| `list` | list many | no |
| `show` | one item's detail | no |
| `read` | item body as Markdown on stdout | **no — enforced** |
| `get` | download to a file | no |
| `search` | query | no |
| `send` | post a message | yes |
| `submit` | submit work | yes |
| `set` | change state | yes |
| `mark-read` | mark as read upstream | yes |

`read` must never issue a non-idempotent upstream request. This rule exists because both
edstem-cli and ontrack-cli currently violate it in different ways.

**The verb may be omitted; it is inferred from the count of positional arguments.**

```
units                    -> units list
units FIT1045            -> units show FIT1045
tasks FIT1045            -> tasks list FIT1045      (nested noun: 1 positional = parent scope)
tasks FIT1045 1.1        -> tasks show FIT1045 1.1
tasks read FIT1045 1.1   -> explicit verb wins
```

This is unambiguous and provably so: identifiers are numeric IDs or unit codes matching
`^[a-z]{2,}\d{3,}[a-z0-9_-]*$`. No identifier can equal `list`, `show`, `read`, `get`, `search`,
`send`, `submit`, `set`, or `mark-read`.

### 2.2 Exit codes

```
0    success
1    other failure (network, unexpected)
2    usage      — bad command, bad flag, bad argument
3    auth       — credentials missing or expired; caller should re-authenticate
4    not_found  — the named entity does not exist
5    upstream   — the server rejected a well-formed request
130  cancelled  — SIGINT
```

Rationale: `2` for usage follows POSIX/GNU. `3` for auth is what edstem-cli already uses and is the
one code automation genuinely needs to branch on. Migration cost per repo:

| Repo | Change |
| --- | --- |
| edstem-cli | usage `1` → `2`. Keeps `3`/`4`/`5`. |
| ontrack-cli | keeps usage `2`, `130`. Adds auth `3`, not_found `4`, upstream `5`. |
| moodle-cli | swap: usage `3` → `2`, auth `2` → `3`. Adds upstream `5`. |

### 2.3 Error codes

One vocabulary:

```
usage | auth | config | not_found | upstream | network | cancelled | unexpected
```

### 2.4 Error output

Exactly **one** error rendering per failure, always on stderr, never on stdout.

Human format:

```
error: <message>
hint: <hint>          # only when a hint exists
```

Structured format (when the resolved output format is JSON or YAML):

```json
{"ok":false,"error":{"code":"auth","message":"Session expired.","hint":"Run `ontrack auth login`."},"exit_code":3}
```

moodle-cli's double-print must be removed: commander's own error output has to be routed through
the shared reporter (`exitOverride` + `configureOutput`), not printed alongside it.

### 2.5 Output format

```
--json            structured JSON
--yaml            structured YAML
--table           force human-readable
--fields a,b      keep only these top-level fields
-o, --output F    write to a file instead of stdout
```

`--json` / `--yaml` / `--table` are mutually exclusive.

**Default is resolved by TTY detection**: stdout is a terminal → `table`; stdout is a pipe or file →
`json`. Humans get tables without a flag; agents get JSON without a flag. This is the single
highest-leverage ergonomic rule in this document.

Removed: `--md` and `--legacy-json` and `--pretty` (edstem). Markdown is produced by the `read`
verb, not by a flag. JSON is always pretty-printed.

### 2.6 Global flags

```
-h, --help
-V, --version
    help [command]
-q, --quiet          suppress non-essential stderr
    --verbose        debug logging  (long form only)
    --no-color       also honour NO_COLOR
-y, --yes            confirm a mutating command non-interactively
    --dry-run        print the plan and exit 0 without mutating
```

`-v` is **not** bound. moodle-cli currently maps `-v` to verbose, one keystroke from `-V` for
version; that binding is removed.

### 2.7 Mutating commands

Every command whose verb is `send`, `submit`, `set`, or `mark-read`:

- interactive stdin → print the plan, then a plain `y/N` prompt;
- non-interactive stdin → require `-y`, otherwise fail with `usage` / exit `2`;
- must accept `--dry-run`;
- must be visible in `--help`. No hidden mutations.

The bespoke typed-phrase confirmations in ontrack-cli (`type "send"`, `type "submit 1.1"`) are
removed in favour of the shared `y/N` prompt.

### 2.8 Self-description

Every tool implements:

```
<tool> commands --json
```

emitting the full command tree: noun, verb, aliases, positionals, options, enum values, and
`mutating: true|false`. SKILL.md is generated from it. moodle-cli and edstem-cli already have
`skills generate`; ontrack-cli gains it.

### 2.9 Environment variables

```
<TOOL>_BASE_URL
<TOOL>_TOKEN
<TOOL>_CONFIG
```

moodle-cli currently has both `MOODLE_URL` and `MOODLE_BASE_URL`; collapse to `MOODLE_BASE_URL`
and accept `MOODLE_URL` as a deprecated fallback that warns on stderr.

Config directory stays `~/.config/<tool>-cli/`.

## 3. `@bunizao/cli-kit`

New package. Keep it small — it exists to delete duplication, not to add a layer. Target under
600 lines of source. If a helper is used by only one tool, it does not belong here.

### 3.1 Exports

```ts
// errors.ts
export type ErrorCode =
  | "usage" | "auth" | "config" | "not_found"
  | "upstream" | "network" | "cancelled" | "unexpected";

export class CliError extends Error {
  readonly code: ErrorCode;
  readonly hint: string | undefined;
  constructor(code: ErrorCode, message: string, hint?: string);
}

export function exitCodeFor(code: ErrorCode): number;
export function normalizeError(error: unknown): CliError;

// output.ts
export type OutputFormat = "table" | "json" | "yaml";

export interface FormatOptions {
  readonly json?: boolean;
  readonly yaml?: boolean;
  readonly table?: boolean;
  readonly fields?: string;
}

/** TTY detection + explicit-flag override. Throws `usage` on conflicting flags. */
export function resolveFormat(options: FormatOptions, isTty: boolean): OutputFormat;

export function render(
  value: unknown,
  options: { format: OutputFormat; fields?: readonly string[]; columns?: readonly [string, string][] },
): string;

/** Writes to stdout or `-o`. Swallows EPIPE and resolves; never throws on a closed pipe. */
export function writeOutput(text: string, options: { output?: string }): Promise<void>;

// report.ts
export function reportError(
  error: unknown,
  format: OutputFormat,
): { readonly text: string; readonly exitCode: number };

// confirm.ts
export interface MutationPlan {
  readonly summary: string;        // multi-line, shown before the prompt
}
export function confirm(
  plan: MutationPlan,
  options: { yes: boolean; dryRun: boolean; interactive: boolean },
): Promise<boolean>;

// program.ts
export function createProgram(meta: {
  name: string;
  version: string;
  description: string;
}): import("commander").Command;   // global flags from §2.6 pre-wired, exitOverride installed

export function mutating(command: import("commander").Command): import("commander").Command;

export function commandsJson(program: import("commander").Command): unknown;

// nouns.ts
export interface NounSpec {
  readonly name: string;                          // canonical, plural
  readonly aliases?: readonly string[];
  readonly verbs: readonly string[];
  readonly defaultByArity: Readonly<Record<number, string>>;  // positional count -> verb
}

/** Rewrites argv so commander always sees an explicit `noun verb ...`. */
export function insertDefaultVerb(argv: readonly string[], nouns: readonly NounSpec[]): string[];
```

### 3.2 `insertDefaultVerb` — the load-bearing piece

This is what makes the omitted verb work without touching commander's parser. It is a pure argv
transform, run before `program.parse()`. Roughly 30 lines. Specify it precisely:

1. Find the first token that is not a global flag. If it does not match a noun name or alias,
   return argv unchanged.
2. Replace that token with the noun's canonical name (this is where `courses` / `projects` →
   `units` happens).
3. Look at the next token. If it is a known verb for that noun, return argv unchanged.
4. If argv contains `--help` or `-h`, return argv unchanged.
5. Count the remaining non-flag tokens. Look up `defaultByArity[count]`. If there is no entry,
   return argv unchanged and let commander produce the usage error.
6. Insert the verb immediately after the noun.

Test this module in isolation. It is the only clever thing in the codebase and deserves a
table-driven test with at least: zero args, alias resolution, explicit verb, `--help`,
flags interleaved with positionals, unknown arity, and a `--` terminator.

### 3.3 Verb enforcement

`commandsJson` validates every registered verb against the §2.1 closed set and throws if a tool
registers something outside it. Each repo asserts this in a unit test. This is how the verb
discipline survives future contributors.

## 5. Execution phases

Phases are ordered by dependency. P0 can start in all three repos in parallel.

### P0 — contract layer, no command renames

Ship-able on its own. Does not change any command name, so it can go out before the rest.

1. Adopt the §2.2 exit-code table.
2. Adopt the §2.3 error vocabulary.
3. Adopt the §2.4 single error rendering. Remove moodle-cli's double print.
4. Adopt §2.5 TTY-based format defaulting.
5. ontrack-cli: add `-h`, `-V`, `help [command]`.
6. ontrack-cli: EPIPE guard, Node version gate, `--force`, pre-auth validation, config hint.

### P1 — build `@bunizao/cli-kit`

Extract from what P0 produced. Sources to harvest: `moodle-cli/src/output.ts`,
`moodle-cli/src/formatters.ts`, `moodle-cli/src/errors.ts`, `edstem-cli/src/output.ts`,
`edstem-cli/src/errors.ts`, `ontrack-cli/src/render.ts`, `ontrack-cli/src/errors.ts`.

Write `insertDefaultVerb` and `commandsJson` new — they have no existing counterpart.

Publish, then have all three depend on it and delete the local copies.

### P2 — ontrack-cli: parseArgs → commander

Isolated to ontrack-cli. `src/cli-app.ts` currently holds two parallel `if` chains: `invoke()`
(lines 395-604) for dispatch and `helpFor()` (lines 135-220) for help text. They are hand-synced
and have already drifted — root-help columns are misaligned for 7 of 15 commands and the `-y, --yes`
option row has an extra space (`src/cli-app.ts:202`). Both chains are deleted; commander plus
`commandsJson` becomes the single source.

Expect the file to shrink substantially. If it does not, the migration went wrong.

### P3 — apply the §4 command mappings

Per repo, independently. Delete old command names outright; the owner has approved breaking
changes. The only aliases retained are the domain-vocabulary ones: `units` / `courses` /
`projects`, all three canonical-equivalent per §0.

**ontrack-cli constraint:** `tests/golden/oracle-required-cases.json` pins argv, stdout digest, and
stderr digest for nine cases, and `npm run verify:oracle` is documented as a merge gate
(`tests/golden/README.md`). The pinned argv are the old spellings (`projects --json`,
`project 1 --json`, `tasks 1 --json`, `roles --json`, `user --json`, `auth check --json`, plus the
`--include-inactive`, `--status`, and `--all` variants). Renaming commands invalidates them.
Regenerate the corpus deliberately in its own commit, state in the message that the argv contract
changed, and keep the underlying captured payloads — the parity claim is about the *data*
projection, not the command spelling. Do not silently `--update` it inside a larger commit.

### P4 — docs and cross-tool tests

1. Regenerate all three SKILL.md files from `commands --json`.
2. Rewrite the three READMEs from one template.
3. Cross-tool conformance test, committed to all three repos:
   - same error class → same exit code in all three;
   - `--help`, `-h`, `-V`, `help <cmd>` all present and exit 0;
   - `commands --json` validates against a shared schema;
   - every verb appears in the §2.1 closed set;
   - every `mutating: true` command rejects non-interactive invocation without `-y` and exits 2;
   - no command named `read` issues a non-GET request (assert via a recording HTTP stub).

## 6. Acceptance criteria

The work is done when all of the following hold in all three repos:

- [ ] `<tool> bogus` exits 2; `<tool> --help` exits 0 and writes only to stdout.
- [ ] An expired session exits 3 in all three tools.
- [ ] Piping any successful command to a file yields JSON; running it in a terminal yields a table;
      neither required a flag.
- [ ] `<tool> commands --json` parses and lists every command with a `mutating` field.
- [ ] No command group and leaf share a name. No two commands differ only by a trailing `s`.
- [ ] Every verb in `commands --json` is in the §2.1 set.
- [ ] `units`, `courses`, and `projects` are interchangeable in all three tools.
- [ ] Every mutating command is visible in `--help` and honours `-y` and `--dry-run`.
- [ ] Piping any command into a consumer that exits immediately produces no stack trace.
- [ ] Each repo's SKILL.md is generated, not hand-written.

## 7. Traps

Things that will bite the implementer, all verified:

1. **ontrack-cli's oracle gate** — see P3. It fails loudly and correctly; do not work around it.
2. **commander's default error behaviour** — it writes to stderr and calls `process.exit` itself.
   `createProgram` must install `exitOverride()` and `configureOutput()` so all errors flow through
   `reportError`. This is exactly what moodle-cli got wrong, producing duplicate output.
3. **`edstem lessons read` is a `PUT`** (`src/ed/client.ts:95`). Renaming it is a behaviour-preserving
   rename, but any script or agent calling it will break loudly. That is the intent.
4. **ontrack `chats <p> <t>` marks comments read** (`src/application.ts:143`). Splitting the read
   path from `mark-read` requires an upstream-behaviour check: confirm whether the history endpoint
   can be called without the read side effect. If it cannot, `chats read` must print a stderr
   warning and the split becomes cosmetic — document whichever turns out to be true.
5. **moodle activity ID namespace** — confirm the six activity types share one ID space before
   merging them into `activities show <id>`. The existing type switch at `src/cli.ts:356-381`
   suggests they do, but verify against a live account rather than assuming.
6. **`-o/--output` is global in edstem, per-command in ontrack.** Making it global everywhere means
   ontrack's download commands need to reconcile `--output` (destination path) with the global
   `--output` (redirect structured output). Pick one: rename ontrack's download destination flag to
   `--dest`, keep `-o` global. Do not let two different meanings share a flag name.
7. **Node version floor differs.** ontrack-cli needs `>=22.5` for `node:sqlite`; the other two do
   not. `cli-kit` must not raise the floor for moodle-cli and edstem-cli.
